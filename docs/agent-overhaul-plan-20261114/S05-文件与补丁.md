## S05-I42 NAS 状态与密钥自愈：坏文件隔离，不再让整个节点起不来
- 问题：`NasPlugin.__init__` 在 `create_app` 里同步构造（`rynmesh/peer_http.py:846-847` `mount_nas`）。`state.enc` 存在时直接 `Fernet((directory/"key").read_bytes())` 并解密（`rynmesh/nas.py:252-255`）：key 丢失、损坏、与状态文件不配套，任何一步抛异常都会让整个节点（包括 agent）起不来。反过来 `state.enc` 不在而 key 在（比如状态文件被清掉）时，`_save`（`:276-288`）因 `self.cipher is None` 用 `open("xb")` 新建 key，必然 `FileExistsError`，此后所有保存失败（添加连接、网盘授权刷新都落不了盘）。Codex 的写锁文件和持久层对坏文件不拖垮进程（`rollout/src/writer_lock.rs:47-51`）。
- 涉及行：G05-34
- 要改：
  - `rynmesh/nas.py:252-255` `__init__` —— 把读 key、解密、`json.loads` 包进 `try/except (OSError, ValueError, InvalidToken, json.JSONDecodeError)`（`InvalidToken` 来自 `cryptography.fernet`）。失败时：`state.enc` 改名为 `state.enc.corrupt-<unix 时间>`（key 缺失/损坏时 key 文件同样改名为 `key.corrupt-<时间>`），以空状态 `{"enabled": False, "sources": []}` 启动，`self.cipher=None`，`self.recovered_from_corruption = {"at": 时间, "reason": 异常类名}`（只记类名）。同时写一行 `warning` 日志。
  - `rynmesh/nas.py:276-288` `_save` —— `cipher is None` 时先看 `key` 文件：存在且能 `Fernet(...)` 加载就复用（此时 `state.enc` 缺失，等于首次保存），读不出才改名为 `key.corrupt-<时间>` 后新建；新建仍用 `open("xb")`，保持"不覆盖别人写的 key"的原语义，但先判断存在避免 `FileExistsError`。S13-I14 把 `_save` 改成 `atomic_write_bytes`、S13-I15 把 key 包进 `os_secret`，复用逻辑要加在 S13 改后的读 key 函数上，不另写读取路径。
  - `rynmesh/nas.py:292-300` `status` —— 返回里加 `recovered_from_corruption`（无则不出现），界面把它显示成一条提示"NAS 连接配置损坏，已重置，请重新添加"；界面文案由 S14 登记，没登记前字段只在接口里。
  - 状态文件损坏时被丢弃的连接密码在 `.corrupt-*` 文件里仍是密文，不额外保留明文；这些备份文件不自动清理，主人可手动删（`status` 里不返回路径）。
- 新增测试：`tests/test_nas_state_recovery.py`（新建，用临时 home）：key 缺失而 `state.enc` 在 → `NasPlugin(home)` 不抛，`state.enc.corrupt-*` 存在，`status()` 含 `recovered_from_corruption`，`sources == []`，之后 `save()` 成功；`state.enc` 是垃圾字节 → 同上；key 在而 `state.enc` 不在 → 第一次 `save()` 复用 key，不抛 `FileExistsError`，重启后能读回；key 内容损坏且 `state.enc` 不在 → key 改名后新建；正常状态读写回归不变。
- 依赖：与 S13-I14、S13-I15 同文件（`nas.py` 的 `_save`/密钥存放），合并时先合它们或同批。
- 兼容和风险：自愈会丢弃已无法解密的连接配置（本来也读不出来），换节点能启动。云盘授权令牌同在该状态里，一并丢失，需要重新授权；这是唯一的数据损失，状态里写明。旧版本写出的正常文件不受影响。
- 工作量：小（<1 天）
- 影响：高

## S05-I43 NAS 文件上传下载改分块流式，大小上限可配置
- 问题：NAS 单文件硬上限 `MAX_FILE = 64 MiB`（`rynmesh/nas.py:24`）。下载 `content`（`:745-755`）先 `plugin.operate(..., "read", ...)` 整块读进内存（WebDAV `request` 累积 `bytearray`，`:178-193`；SMB `read` 一次 `f.read(limit+1)`，`:129-134`），再用 `io.BytesIO` 假装流式返回；上传（`:757-766`）把整个请求体累积在 `bytearray`，超 64 MiB 返回 413。视频、安装包、照片原片等常见大文件根本无法下载或上传，且每次占用等于文件大小的内存。Codex 文件系统抽象按块读写而不是整块（`file-system/src/lib.rs:46-49`）。
- 涉及行：G05-37
- 要改：
  - `rynmesh/nas.py:24` —— 新增 `STREAM_MAX_FILE = 4 GiB` 的默认值和 `plugin.state["max_file_bytes"]`（可配置，`status` 里 `max_file_bytes`（`:300`）返回实际值）。agent 读取路径（`ai`/资源读取）继续用 `MAX_PREVIEW`/资源自己的上限，不受影响；原 `MAX_FILE` 常量只保留给内存型调用（`_perform` 的 `read` 动作、`:576` 的 `len(data)` 检查、图片 `MAX_IMAGE`）。
  - `rynmesh/nas.py:129-134`（SMB）与 `:178-193`（WebDAV）—— 连接器新增 `iter_read(path, chunk=1 MiB)`（生成器）：SMB 用 `open_file(mode="rb")` 循环 `f.read(chunk)`；WebDAV 用 `client.stream("GET")` 的 `iter_bytes(chunk)`，状态码检查沿用 `request` 的映射（`:179-187`）。新增 `write_stream(path, chunks)`：SMB 临时文件按块写再 rename（沿用 `:136-149` 的临时文件做法）；WebDAV `PUT` 传生成器作 `content`（需要 `Content-Length` 时先由调用方带入）。网盘连接器（Google/百度/OneDrive）没有这两个方法时回退到现有整块路径，仍受 64 MiB 限制，响应里 `status.max_file_bytes` 按协议区分。
  - `rynmesh/nas.py:563-600` `_operate` —— 新增 `operate_stream(source_id, action, path)`，只用于 `read`：检查授权后返回 `(connector, iterator)`，用一次性连接（见 S05-I19 的 G05-40 条：读不占 gate），迭代结束或客户端断开时关闭连接；`len(data) > MAX_FILE` 检查不适用于流式分支，改由下载计数超过 `max_file_bytes` 时中止。
  - `rynmesh/nas.py:745-755` `content` 下载分支 —— 去掉 `BytesIO`，直接 `StreamingResponse(plugin.operate_stream(...), ...)`；响应头保留；能拿到大小时加 `Content-Length`（SMB `stat`、WebDAV 的 `getcontentlength`，拿不到不设）。
  - `rynmesh/nas.py:757-766` `upload` —— 用 `tempfile.SpooledTemporaryFile(max_size=8 MiB)` 接 `request.stream()`，累计超过 `max_file_bytes` 返回 413；完成后 `run_in_threadpool(plugin.operate_stream_write, ...)` 把文件对象按 1 MiB 块交给 `write_stream`，不再 `bytes(data)`。`write` 动作（agent 与网盘）仍走原整块路径。
- 新增测试：`tests/test_nas_stream.py`（假 SMB/WebDAV 连接器）：100 MiB 假文件下载，峰值内存增量小于 20 MiB（用 `tracemalloc`），读到的哈希一致；客户端中途断开后连接被关闭；上传 100 MiB 到假连接器按块写入且哈希一致；超过 `max_file_bytes` 返回 413 且目标文件不残留；网盘连接器仍走原路径且受 64 MiB 限制；`status()["max_file_bytes"]` 反映配置。
- 依赖：S05-I19（读不占 gate、一次性连接）；与 S05-I17（覆盖写）、S13-I14/I15 同改 `nas.py`，同批合并。
- 兼容和风险：下载响应由整块变流式，客户端会先收到头再收数据，中途出错表现为连接中断而不是一个 JSON 错误，界面下载需按失败处理；上传超大文件落临时磁盘，要保证临时目录有空间，放在 `home/plugins/nas/tmp`（0700，启动时清理遗留）。SMB 大文件写不是原子（临时文件加 rename，沿用）。
- 工作量：中
- 影响：中
