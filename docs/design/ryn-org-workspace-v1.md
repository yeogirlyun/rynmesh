# Ryn 组织空间与组织插件 v1 设计

状态：已作废（2026-10-21）。组织不进 Ryn 核心，改为公司插件，见 [ryn-company-plugin-v1.md](ryn-company-plugin-v1.md)。

## 0. 已确认的决策

| 问题 | 决策 |
| --- | --- |
| 组织节点 | 企业自己部署 |
| 员工认证 | 第一个身份源是企业微信扫码登录；接口按"身份源适配器"设计 |
| 组织聊天记录 | 组织可读（非端到端加密） |
| 业务数据 | 每个组织用自己的数据后端，Ryn 不保存业务数据 |
| 产品目标 | 替代企业微信；移动端后续做 |

## 1. 要解决的问题

一个"组织"由四部分组成：

- 一台自部署的**组织节点**
- 一批**成员**，每个成员名下有多台设备
- 一组**组织插件**
- 组织 **IM**

组织插件让每个组织把自己的数据后端（财务、ERP、HR、CRM、自研系统）接进 Ryn。员工在 Ryn 里以本人身份使用这些系统，入口有三个：应用页面、Agent 工具、消息卡片。

数据留在组织自己的后端，Ryn 只负责四件事：认证、转发、展示、审计。

可以类比企业微信的"自建应用"：企业微信提供身份、消息、回调，业务由企业自己的后端实现。Ryn 组织插件对应同样的角色，并且多出 Agent 工具这一能力面。

## 2. 总体架构

```
 员工设备（Ryn）                       组织节点（企业自部署，唯一对外入口）                  组织内网
┌──────────┬───────────┐          ┌──────────────────────────────────┐
│ 个人空间  │ 组织空间    │          │ 身份：身份源适配器 / 成员 / 设备证书   │──> 企业微信（第一个身份源）
│          │ · 应用页面  │─设备会话─>│ 插件网关：注册表 / 身份转发 / 工具聚合 │──组织断言──> 业务后端 A（财务）
│          │ · Agent 工具│ 加密传输  │ 组织 IM：会话 / 机器人 / 卡片       │──组织断言──> 业务后端 B（HR）
│          │ · 组织 IM   │          │ Org API / 事件回调 / 审计          │<─Org API───  业务后端 C（自研）
└──────────┴───────────┘          └──────────────────────────────────┘
```

原则：

1. **组织节点是唯一入口。** 设备不直连业务后端，也不直连企业微信。业务后端不需要暴露到公网，员工在外面也能通过 Ryn 使用内网系统。
2. **凭证只在组织节点。** 身份源的 Secret、各业务后端的服务凭证都不下发到设备。
3. **认证在组织节点，数据权限在后端。** 组织节点告诉后端"这是谁"，后端自己决定"能看什么"。
4. **插件对等。** 组织节点自带的功能（审批、公告等）也用同一套插件框架实现，保证第三方插件拿到的能力是够用的。

## 3. 组织身份

### 3.1 三层身份

```
组织根密钥（离线备份）
  └─ 签发密钥（在组织节点上，可以轮换）
       ├─ 组织节点证书
       └─ 成员 member_id ←→ 外部身份 {wecom: userid, …}
            ├─ 设备证书：张三-办公室 Windows
            └─ 设备证书：张三-MacBook
```

- **成员**：内部 `member_id` 随机生成，通过外部身份映射。例如企业微信是 `(corpid, userid)`；userid 可能被管理员修改，所以不拿它直接当主键。
- **设备**：每台设备入组时生成独立的组织设备密钥，不复用个人 peer_id，避免把员工的个人 mesh 活动和工作身份关联起来。私钥由系统密钥库保护（DPAPI / Keychain）。
- **设备证书**：组织签名，内容是"device_pub 属于 member_id"。有效期 7 天，在线时自动续期。

### 3.2 身份源适配器

```python
class IdentityProvider:
    def login_url(self, state) -> str: ...          # 扫码或跳转登录
    def exchange(self, callback) -> ExternalSubject: ...  # 服务端校验，拿到外部身份
    def sync_directory(self) -> Directory: ...       # 部门与成员，用于离职自动停用
    def notify(self, subject, text) -> None: ...     # 可选：新设备提醒
```

- **v1 只做企业微信。** 流程是：登录链接 → 回调拿到 code → 用 Secret 调 `auth/getuserinfo` 换 userid。
- **备用路径：** 自有的"邀请 + 审批 + 旧设备担保"，为将来真正脱离企业微信准备。
- **以后接入：** 钉钉、飞书、通用 OIDC。

### 3.3 入组（申请加入）

1. 设备生成组织设备密钥，向组织节点发起入组请求，拿到 `enroll_id` 和登录链接。`state` 是一次性的，并绑定 device_pub。
2. 员工用企业微信扫码。组织节点在服务端用 code 换到 userid，这一步设备无法伪造。
3. 按策略处理：属于自动通过的部门就直接签发证书；否则进入管理员审批队列，也就是"申请加入"。
4. 设备用私钥签名轮询，领取证书。别人截获了二维码也领不走证书。
5. 通过身份源通知本人："新设备已加入，不是你本人请停用。"

**同一员工的第二台电脑**：同一个外部身份对应同一个成员，于是得到第二张设备证书。

**离职**：身份源同步发现员工被禁用或删除后，自动停用成员并吊销全部设备证书。

### 3.4 设备会话

设备用私钥签名换取 15 分钟的会话 token。组织节点每次请求都检查：会话 → 证书 → 设备是否吊销 → 成员是否在职。

## 4. 组织插件模型

### 4.1 三种运行形态

| 形态 | 运行位置 | 数据位置 | 用途 |
| --- | --- | --- | --- |
| **后端插件**（主力） | 组织自己的业务后端 | 业务后端 | 把已有系统接进 Ryn：财务、ERP、HR、CRM |
| **内置插件** | 组织节点进程内 | 组织节点 | 替代企业微信的通用功能：审批、公告、通讯录、打卡 |
| **本地插件** | 员工设备 | 设备 | 必须在本机执行的能力（文件处理、桌面自动化），由组织统一下发；v1 不做 |

### 4.2 四个能力面

一个插件可以声明以下任意组合：

| 能力面 | 员工看到的 | 实现方式 |
| --- | --- | --- |
| **应用页面** | 组织空间里的一个 App | 组织节点反向代理后端的 Web 页面，或使用插件包里的静态页面 |
| **Agent 工具** | Ryn Agent 能调用的工具 | 来源可以是后端的 MCP、OpenAPI 或 manifest 里的内联定义，由组织节点聚合 |
| **机器人与卡片** | IM 里的插件机器人、可点击的卡片 | 后端调用 Org API 发消息；卡片按钮通过回调交给后端处理 |
| **通知与事件** | 系统通知、角标 | 后端调用 Org API；组织节点把成员变动等事件推给后端 |

### 4.3 接入等级

让已有系统按需接入，逐级加码：

- **L0 只要页面**：后端加一个"校验组织断言"的中间件，替代它自己的登录。现有 Web 系统几乎不用改。
- **L1 加工具**：提供 MCP 端点或带 `x-ryn-effect` 标注的 OpenAPI，Agent 就能直接用。
- **L2 加消息**：通过 Org API 发卡片、发通知、接收回调。审批、告警这类流程走这一级。

## 5. 插件协议

### 5.1 Manifest

```json
{
  "schema": "ryn.org-plugin.v1",
  "id": "finance",
  "name": "财务",
  "version": "1.2.0",
  "backend": { "base_url": "http://10.0.0.5:7001", "identity": "assertion" },
  "surfaces": {
    "app":   { "mode": "proxy", "entry": "/" },
    "tools": { "source": "mcp", "path": "/mcp" },
    "bot":   { "name": "财务助手", "events": "/ryn/events" }
  },
  "scopes": ["directory.basic", "message.send", "notify"],
  "tools_policy": { "default_effect": "read" },
  "data_policy": { "device_cache": "session", "model": "org_only" }
}
```

- 服务凭证不写在 manifest 里，由管理员在组织节点单独配置。
- `effect` 分三级：`read`、`write`、`irreversible`（比如付款）。`write` 和 `irreversible` 在 Ryn 里需要员工确认；`irreversible` 每次都要确认。
- `data_policy.model`：`org_only` 表示工具结果只能交给组织批准的模型。

### 5.2 身份传递：组织断言

组织节点每次转发请求时，**删除**客户端带来的所有身份类请求头，然后注入：

```
X-Ryn-Org-Assertion: <JWT，RS256/ES256>
{
  "iss": "https://ryn.company.com",
  "aud": "plugin:finance",
  "sub": "m_8f3a…",
  "ids": { "wecom": "zhangsan" },
  "name": "张三", "departments": ["财务部"], "roles": ["member"],
  "device": "d_21c…", "via": "app | agent | bot",
  "exp": "<now + 60s>", "jti": "…"
}
```

- 后端用 `https://ryn.company.com/.well-known/jwks.json` 验签。主流 JWT 库都能做，我们再提供 Node / Python / Java 的中间件 SDK。
- `aud` 绑定插件，插件 A 拿到的断言不能拿去调用插件 B。60 秒过期，用 `jti` 防重放。
- `via` 让后端知道这次调用来自页面、Agent 还是机器人，可以对 Agent 调用单独限权或单独审计。
- **兼容模式**：老系统暂时不验 JWT 时，可以用服务 token 加可信请求头。这种方式安全性弱（持有 token 的人能冒充任何人），管理页上会明确标出风险。

### 5.3 Org API（后端 → 组织节点）

用插件凭证认证：安装时注册插件公钥，调用时带签名 JWT；简单场景也可以用 secret。能调用哪些接口受安装时批准的 `scopes` 限制。

| 接口 | scope |
| --- | --- |
| `POST /org-api/v1/messages`：给成员或会话发文本 / 卡片 | `message.send` |
| `PATCH /org-api/v1/cards/{id}`：更新卡片状态（如"已审批"） | `message.send` |
| `POST /org-api/v1/notifications` | `notify` |
| `GET /org-api/v1/directory/…`：在插件可见范围内查部门和成员 | `directory.basic` / `directory.contact` |

### 5.4 事件回调（组织节点 → 后端）

事件包括 `card.action`、`bot.message`、`member.joined`、`member.left`、`member.updated`、`plugin.installed`。组织节点对回调签名，后端用同一个 JWKS 验证。

## 6. 权限：三层

| 层 | 谁负责 | 管什么 |
| --- | --- | --- |
| 1. 可见性 | 组织节点 | 哪些部门、角色、成员能看到和使用这个插件；插件能调用哪些 Org API |
| 2. 操作级 | 组织节点按 manifest 执行 | 某些工具或路径要求特定角色；`write` 和 `irreversible` 要求确认 |
| 3. 数据级 | 业务后端 | 这个人能看哪些公司、部门、记录；后端根据组织断言自行判断 |

组织节点不复制业务系统的细粒度权限，各个后端保留自己的权限模型。

## 7. 安全与数据边界

- 设备永远不直连后端；所有凭证都只在组织节点上。
- 断言短期有效、绑定插件、防重放；转发前先清理客户端带来的身份头。
- **模型策略**：组织空间里的 Agent 只能使用组织批准的模型（由组织节点配置模型网关）。`org_only` 插件的工具结果不会进入员工的个人模型 provider。
- **页面沙箱**：每个插件页面使用独立 origin 的 iframe 或 webview，通过 `ryn.org.*` 桥接 SDK 与外部交互（获取上下文、调用工具、请求确认、打开会话）。插件页面访问不到个人空间。
- **设备缓存**：遵循 `device_cache` 的设置（`none` / `session` / `persistent`）。停用后设备删除组织数据；离线或被篡改的设备无法保证删除，这一点与企业微信相同。
- **审计**：每一次转发、工具调用、Org API 调用都记录"谁 / 哪台设备 / 经由什么 / 哪个插件"，追加写入并做 hash 链。

## 8. 插件生命周期

```
开发（manifest + 后端中间件）→ 管理员注册（后端地址、服务凭证）→ 审核 scopes 与可见范围
→ 启用（组织节点签名后发布到成员目录）→ 更新（扩大权限需要重新审核）→ 停用（立即失效，后端数据保留）
```

## 9. 组织 IM

- **存储**：组织节点，组织可读；传输使用 TLS 加设备会话，落盘加密。
- **功能**：单聊、群聊、文件、已读、撤回（保留审计副本）、离线增量同步；新设备拉取多少历史由组织策略决定。
- **插件机器人**：插件作为会话成员出现，可以发卡片、接收 `@`、处理按钮回调。审批、告警、Agent 结果分享都通过这里完成。
- **与个人聊天的关系**：和个人好友聊天完全分开，界面上标明"组织可见"。

## 10. 设备端组织空间

- 数据放在 `home/orgs/<org_id>/`：密钥、证书、IM 缓存、组织 Agent 会话、插件页面的会话数据。
- 组织 Agent 看不到个人记忆、个人文件和好友；个人 Agent 看不到组织数据。
- 一台设备可以加入多个组织，各自隔离。界面上用侧边栏切换空间；组织插件显示在 Apps 页的组织分区里。
- Agent 通过组织节点的统一 MCP 端点 `/mcp` 获取当前成员可用的全部工具，工具名带命名空间 `plugin.tool`。

### 11.3 可复用的现有代码

- `crypto.sign_payload`：证书、签名声明

## 12. 分期与验收

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **M1 身份闭环** | 组织节点、企业微信身份源、成员/设备/证书、会话、审批入组、吊销、离职同步、设备端组织空间、管理页 | 同一员工两台电脑扫码后归到同一个成员；停用后立即失效；企业微信里禁用员工后自动停用 |
| **M2 插件框架（L0 + L1）** | manifest、注册与审核、身份转发与 JWKS、应用页面代理、工具聚合 MCP、三层权限、模型策略、审计 | 用两个技术栈不同的已有后端验证，除加断言中间件外零改动；伪造身份头无效；越权调用被拒绝 |
| **M3 IM 与插件消息（L2）** | 组织 IM、插件机器人、卡片、回调、通知 | 后端发审批卡片 → 员工点按钮 → 后端收到回调并更新卡片 |
| **M4** | 内置插件（审批、公告、通讯录）、SDK、本地插件、移动端、高可用 | 另行定义 |

## 13. 待确认

1. 内置功能（审批、公告等）是否用同一插件框架实现？建议用，自己先用过，框架才够第三方用。
2. 插件页面：优先代理现有 Web 系统，还是要求重写成插件包？建议两种都支持，代理优先，接入成本最低。
3. M2 用哪两个已有后端做验证？
4. 组织 Agent 使用的模型网关由谁提供（组织自有 API Key、自建模型，还是我们提供）？
5. 是否需要跨组织分发插件（插件市场）？v1 不做，但 manifest 格式预留。
6. 组织节点需要公网域名和固定出口 IP（企业微信可信域名 / 可信 IP 的要求），部署文档要写明。
