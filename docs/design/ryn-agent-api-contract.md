# Ryn Agent integration contract

The T02/T03 field authority and control contract is specified in
`docs/acceptance/ryn-agent-delivery/cases-runtime-contract.md`. The additions below
are implemented; the original v1 compatibility interface is retained underneath.

## Current control, scope and verification additions

- Create accepts optional `scope:{resources:[{connection_id,root_path,recursive?,actions}],allow_model_data:true}` and `expected_destination_revision`. Nonempty scope requires the exact selected catalog row's nonempty `destination_revision` and a bridge that supports destination binding. Scope preparation precedes the single encrypted task-create transaction; failure creates no task. The complete request, including scope and revision, participates in durable idempotency.
- GET `/resources` includes `create_scope_supported`. GET `/tasks/{id}/scope` returns `scope` (including owner form `selection`), `scope_revision`, `control_revision`, `model_destination` and `current_model_destination` (or null). Destinations contain `catalog_model_id`, `provider_peer_id`, `source_id`, `destination_revision`.
- PUT `/tasks/{id}/scope` accepts `scope`, `expected_control_revision`, `expected_scope_revision`, optional UUID `client_request_id`, and requires `expected_destination_revision` for nonempty resources. Empty revocation remains possible when the model disappears. Explicit reauthorization changes destination and provider-history epoch atomically: old derived tool/assistant/summary content remains encrypted audit, never new provider input.
- Owner actions prefer `expected_control_revision`; legacy `expected_revision` remains a compatibility lock. Pause/cancel deliberately do not fail on stale versions. Messages additionally accept `intent:steer|information` and `expected_goal_revision`; answer accepts `action:answer,pending_input_id,answers,expected_goal_revision`. Exact idempotent replay requires the entire original request including original versions. Conflict returns `detail` plus `current` task.
- `allowed_actions` is authoritative UI capability metadata. A running model response is discarded after an owner control change; already executed tool evidence is retained. Question answers have trusted UI metadata `{kind:input_answer,prompt,pending_input_id,fields:[{label,value}]}` under `message.ui`; ordinary owner additions have `{kind:steer|information|message,text}`. UI metadata never goes to a provider.
- `model.complete(..., *, expected_destination=None)` and `supports_destination_binding=True` bind the actual immutable adapter to the exact authorized generation on every resource-bearing main/summary/verification request. Stable source IDs alone are insufficient. Local API sources, strictly verified native bindings and authenticated friend/space peer bindings now have destination checks; see `peer-model-binding-t15-contract.md`. Unverified rows and CLI destinations still reject resource egress. Local integration tests do not establish actual native inference or two-physical-host acceptance.
- Business tools register code-owned `verification_specs()` and `verify(receipt, criteria, *, context, cancelled)`. The runtime records exact operation receipts before/after dispatch. A planner's final answer starts separate mechanical reads followed by an independent no-tool semantic assessment of all ordered owner requirements, candidate answer, actual receipts and mechanical evidence. This assessment counts against task model-call/time/context/output limits.
- `outcome.verified` requires all required checks passed, at least one registered mechanical check, and the semantic checker citing current supplied mechanical evidence IDs. Old goal/epoch evidence and empty business evidence references are rejected. Pure semantic answers need no plan; their semantic assessment is visible separately while an unclassified goal without mechanical proof remains `unverified`. Mechanical failure cannot be overridden by either model. `verification_evidence` exposes bounded real readback records; the original candidate text remains audit, never evidence by itself.
- Unknown writes may query `tools.reconcile(operation_id, *, context, cancelled)` once automatically, then through explicit `action:reconcile` (at most three attempts within the task's active-time budget). The context includes the executor's original `operation` receipt. Only matching operation ID, tool, argument digest and attributable business receipt can resolve it. Current matching state alone remains unknown. Exact confirmed execution may continue automatically only when original goal/control/scope/epoch/authority and current destination/permissions remain valid, with no owner pause/cancel/disable or exhausted budget. Other outcomes remain paused or unknown. Recovery closes the original tool pair, never resubmits the write, and invalidates old queued proposals. `reconciliation` exposes state/attempts/reason; unresolved tasks cannot resume or change scope.

These fields do not imply support for all planned file/source workflows. A missing
business verifier or exhausted verification budget remains explicitly unverified.

## Generic reporting and checker policy (v2.5)

The planner and independent no-tool checker must distinguish observed failures from untested causes, missing records from historical absence, repeated views from independent evidence, and compare timestamps/numbers correctly. Existing permission, mechanical verification and bounded repair behavior are unchanged. Real Q02 revalidation still contains unsupported fault-scope claims accepted by the checker; this policy addition is not proof that semantic false positives are solved. Non-author Astra review and final matched-model evaluation remain pending.

## Contradictory semantic assessments (v2.6)

A well-formed checker response that reports `passed` while listing nonempty `uncovered_requirements` is conservatively normalized to `unknown`. All original shape, current goal/epoch and required mechanical evidence checks still apply before normalization. The result retains `reported_status:passed`, the original gaps and `normalization_reason:reported_pass_with_uncovered_requirements`; the runtime records `verification_assessment_normalized`. This may enter the existing single bounded correction round, never grant new authority or replay a write. Invalid or missing evidence remains invalid. Restart tests cover normalization, correction and one-write-only behavior; the latest live P06 passed without exercising normalization. This change does not resolve the separate Q02/Q03 semantic false positives.

## Per-model sharing scope and recipient preview (2026-10-10)

- `ryn_set_model_sharing` accepts optional `scope: personal_space | friends`, alongside the exact catalog `model_id` and `enabled`. Omission preserves the current scope. API/local sources support both scopes; the native model branch currently supports only personal-space scope and explicitly rejects `friends`.
- Preview binds the old/new flag and scope, encrypted source configuration revision, and **all allowed grants for this exact model service**, including grants whose relationship is currently inactive. More than 100 recipients is rejected rather than silently truncating approval. The UI displays both scopes and distinguishes a saved grant from an active relationship or a successful receiver probe.
- Execution holds the existing space/source/native locks and the permission-store transaction across preview comparison and source save. A changed recipient set invalidates the approval. A concurrent owner grant update is serialized after the source commit. Scope and sharing are saved together without changing siblings, credentials or the future-task default.
- The tool does not mutate friend grants. A currently private model can be prepared with `enabled:false, scope:friends`, then receive an exact `ryn_set_friend_model_access` grant, then be enabled. These are separate approved business writes. This flow does **not** satisfy frozen R02's single-effective-write requirement; an integrated sharing transaction/recovery design remains necessary. Do not pre-enable the model, pre-grant its receiver, or collapse multiple writes in the collector to make that case pass.
- Mechanical verification checks both flag and scope and explicitly limits its claim to configuration readback. Development tests also perform signed/encrypted receiver dispatch through production admission and an actual authenticated loopback HTTP synthetic upstream: private+grant denied, exact peer allowed after enablement, another peer with copied grant denied, and revoked/disabled access denied. The peers are local, the upstream is deterministic; this is not real-model or two-physical-node acceptance.
- Sharing/grant operation reconciliation still relies on the process-local exact receipt cache. A restart after a business commit but before a durable task receipt remains unknown and must not replay the write. This change does not claim durable sharing recovery or cancellation of all already-admitted requests on scope changes.

## Agent-managed default for future tasks

- `ryn_get_agent_configuration` returns `settings_revision` from the same encrypted snapshot as the settings. Existing HTTP settings payloads retain their shape. Every actual owner settings change increments the internal revision; an A→B→A change invalidates old approvals.
- `ryn_set_default_agent_model({model_id,expected_settings_revision})` is a registered write tool. It accepts only an exact available, Agent-capable model with a verifiable destination. Preview binds the current/default target, source/node/destination generation and settings revision. The ordinary runtime exact approval or task-and-current automatic allowlists apply.
- Dispatch rechecks the current task, goal/control/scope, caller identity, runtime-issued in-flight capability, permissions, preview and settings CAS. The transaction changes only `settings.model_id` plus internal revision/binding metadata, and stores an attributable operation receipt in that task in the same encrypted commit. It cannot enable Agent, change permission modes/budgets, switch the running task, transfer its history/grants, or publish a model.
- Future tasks selecting this saved default, including the UI's explicit model-id path, inherit its approved destination binding. A retargeted source is rejected before task creation or subsequent inference. Explicit owner reselection through settings supersedes that binding. A concurrent settings update during implicit/default-bound creation rejects the stale creation rather than silently selecting the wrong default.
- Mechanical verification compares the atomic receipt, saved settings and current destination; current matching state alone does not establish a lost operation. Recovery queries the exact durable operation ID and argument digest, without reissuing the mutation. Later owner control changes remain authoritative for whether execution may continue.
- The approval card shows old/new stable IDs, the new model/source/provider, and the future-task-only scope. Deterministic store/runtime tests and frontend tests are development evidence. Non-author Astra review, live model exercise and the full frozen C03 receiver-sharing/two-node scenario remain required.

## Internal context checkpoint contract (v2.4)

- Checkpoints are a lossy model-context projection; original encrypted history is retained. Current owner instructions and mutation receipts remain exact, and model/permission changes invalidate the checkpoint with the history epoch. A generated summary never grants authority.
- `context_checkpoint.references` is an internal map from deterministic `ref_` labels to exact opaque values from known resource-tool arguments/results. Only designated reference fields are projected; user prose and embedded file text are not parsed or rewritten. Tool dispatch still requires the full authenticated value and revalidates original provenance/current scope. Labels are not capabilities or accepted tool aliases.
- Maps are deduplicated and bounded to 128 values. All exact values count against the actual request context budget; excessive retained state stops the task instead of dropping authorization evidence or exceeding the limit. This does not yet solve unlimited long-task reference growth.
- Reloadable business schemas may be released when compaction cannot fit retained state. `tool_menu_changed.reason=context_space` records this event. Tools must be rediscovered/reloaded before invocation; exposure checks and business permissions remain enforced. The reference host uses the same schema release rule.
- No-tool summary calls share main-task model-call/time/token budgets. Unusable responses retain sanitized finish reason and actual usage; at most one bounded retry is persisted. F08 still fails real-model development evaluation; these mechanisms are not evidence that small-window long-document work has passed.
- Semantic verification treats an unusable empty response with `finish_reason=length` as an invalid verification response. It shares the existing single persisted format-repair allowance with invalid JSON; it does not add another retry allowance or replay business writes. Actual failed-call usage is settled before retry admission. Pause, cancellation, disablement and step/time/token limits still prevent dispatch; other response rejection reasons do not receive this format retry. Regression tests cover restart, repeated failure, control changes and exhausted steps. The latest successful real C03 run did not trigger this branch, so real recovery effectiveness remains unverified.

Agent is optional, node-owned and independent of stateless inference sharing. All APIs require the existing local_control guard; all responses use Cache-Control: no-store. Snake case JSON throughout.

## Owner credential, guidance and lifetime accounting additions

- POST `/api/local/agent/tasks/{id}/source-credential` takes a UUID `client_request_id`, `expected_control_revision`, `expected_goal_revision`, optional bound `pending_input_id`, `kind:api|local`, exact `base_url`, `source_id` (empty for a new source), and either `api_key` or `reuse_existing:true`. Existing credential reuse may additionally supply `expected_source_revision`; the stored slot always binds the actual source revision read. Keys never appear in the task or returned metadata. DELETE on the same path revokes the exact slot with the same owner control fields and endpoint identity. A normal `answer` cannot answer a `credential_ref` question. `ryn_list_source_configurations` returns the opaque `source_revision` for each source so the Agent can distinguish concurrently changed configurations; this is an identity token, not an ordered version number or connectivity proof.
- A credential response is `{credential:{has_credential,kind,base_url,source_id,credential_version,expires_at},task}`. Slots last one hour and bind task/owner/node/goal/endpoint; changing a source invalidates old reused-key slots. Task deletion and credential changes share a gate. A control race may leave a locally stored slot while returning `agent_credential_changed_control_conflict`; the UI must not say that storage definitely did not occur.
- The credential form posts only to this dedicated API. Its secret and exact uncertain retry body stay in component memory; neither is persisted to browser storage or normal chat drafts. An explicit retry retains the original UUID, versions and body. Leaving the page clears this form. Preparing and testing source drafts do not change the active source; commit requires approval of the exact tested draft. Synthetic probe requests can consume model usage.
- GET `/skills` returns versioned built-in guidance. Task creation accepts explicit `skill_ids`; selected content/version is snapshotted. GET `/preferences` and PUT `/preferences` (`{expected_revision,items:[{id,text}]}`) expose owner-controlled encrypted preferences with revision CAS. Skills/preferences cannot grant access, modify the goal or serve as execution evidence. There is no model tool to save preferences.
- Task creation accepts `budget_limits` with `max_total_model_calls`, `max_total_tool_calls`, `max_total_tokens`, `max_total_seconds`. PUT `/tasks/{id}/budget` uses server-granted action availability and control revision. Public `budget` separates lifetime/current-round totals, known usage, conservative charged usage, unknown cost and unsettled operations. New turns do not reset lifetime spending.
- Model, compaction, verification and draft probe calls share durable admission and settlement. Business reads/writes, mechanical verification and reconciliation consume the tool allowance. Missing reported token usage remains null and keeps its reservation; a crash never refunds unknown work. Output allowance may shrink only for an adapter that enforces it; otherwise insufficient full allowance rejects before dispatch. Further whole-feature tests and UI wiring remain necessary; these contracts are not formal acceptance claims.

## Python boundary

`AgentRuntime(AgentStore(root, messaging_key), model, tools, catalog)`.
- `catalog.list_models() -> list[dict]`, stable `id`, `name`, `source` (`local_api`, `local_service`, `peer`), `available`, `agent_supported`, `tool_support` (`supported`, `unsupported`, `unknown`), optional `description`. Never expose credentials. Both available and agent_supported are required by backend model selection.
- `model.complete(model_id, messages, tool_specs, cancelled, on_event) -> {"message": {"role":"assistant", "content":str|null, "tool_calls":[{"id":str,"type":"function","function":{"name":str,"arguments":str(JSON object)}}]}, "usage":dict}`. Synchronous, bounded network timeout, checks cancelled callback; model and peer requests run on consumer, no tools delegated to providers. on_event(dict) is optional metadata, never reasoning/secrets.
- `tools.specs() -> list[OpenAI function tool spec]`.
- `tools.metadata(name) -> {"effect":"read"|"write", "title":str, "risk"?:str, "preview_precondition"?:bool}`. Unknown tool raises ValueError. Every mutation MUST declare write.
- `tools.preview(name, arguments) -> dict` is read-only and deterministic, with before/after state and relevant configuration revisions. Runtime hashes it for approval and rechecks before dispatch.
- `tools.execute(name, arguments:dict, *, operation_id:str, cancelled:Callable, expected_preview?:dict) -> dict` (JSON safe, sanitized, bounded; result includes useful evidence). For metadata preview_precondition=true writes, runtime passes expected_preview and business layer rechecks it under target storage locks. operation_id is stable per invocation; do not automatically retry writes. Existing business services retain authorization checks.
- `AgentToolRejected` from `agent_runtime.store` guarantees no side effect occurred; raise only before mutation. Runtime records a `not_executed` error receipt and returns control to the model for inspection/correction with a new approval. Unclassified exceptions after a write's dispatch marker remain ambiguous and cannot resume. Read-only failures can return error receipts for bounded model correction.
- `build_agent_integrations(app, store, home) -> (model, tools, catalog)` in `rynmesh.agent_runtime.bridge`.

## HTTP

Full task and summary objects include the task's original `permission_mode` and `allowed_write_tools` snapshots, independently of current settings.

- GET `/api/local/agent/settings` -> settings object `{enabled:false, model_id:"", permission_mode:"confirm_changes", allowed_write_tools:[], max_steps:16, max_seconds:180, max_context_chars:60000, max_output_chars:20000}`.
- PUT `/api/local/agent/settings` accepts partial settings object, returns settings. permission_mode `read_only`, `confirm_changes` or `automatic`; enable is independent of sharing. Automatic execution requires a known write-tool name in BOTH the task's snapshotted allowlist and current settings allowlist, and both task/current mode must be automatic. All other writes still require approval. Disabling pauses active tasks; re-enabling does not automatically resume them.
- GET `/api/local/agent/models` -> `{models:[catalog rows]}`.
- GET `/api/local/agent/tools` -> `{tools:[{name,effect,title,risk?,supports_preview?,preview_precondition?}]}`.
- GET `/api/local/agent/tasks` -> `{tasks:[task summaries]}` newest first.
- POST `/api/local/agent/tasks` `{message:str,model_id?:str,title?:str,client_request_id?:UUID}` -> full task, HTTP 200. Agent must be enabled; model defaults settings.model_id. A repeated client_request_id with identical request returns the existing task; changed request gives agent_request_conflict. Server owns system instructions and all tool messages.
- GET `/api/local/agent/tasks/{id}` -> full task.
- POST `/api/local/agent/tasks/{id}/messages` `{message:str,expected_revision:int}` -> full task. Only completed/failed/paused tasks with no unresolved write may receive a new user turn.
- POST `/api/local/agent/tasks/{id}/actions` `{action:"pause"|"resume"|"cancel"|"approve"|"deny",expected_revision:int,approval_id?:str}` -> full task. Approve/deny must include exact pending approval id and revision; no client tool arguments/results accepted. Resume interrupted ambiguous-write tasks forbidden; create a new task to inspect actual service state.
- GET `/api/local/agent/tasks/{id}/events?after=0` -> `{events:[event], cursor:int, status:str, revision:int}`. Poll at ~1 second while active.

Task full shape: `{id,client_request_id,title,model_id,status,revision,created_at,updated_at,messages:[{role,content,tool_calls?,tool_call_id?}],events:[{seq,type,at,...}],pending_approval:null|{id,tool,arguments,call_id,arguments_sha256,preview,preview_sha256,title},steps:int,result:str,error:null|str,limits:settingsSubset}`. Summaries omit messages/events but include pending_approval. Status `queued`, `running`, `waiting_approval`, `paused`, `completed`, `cancelled`, `failed`, `interrupted`. Events include `created`, `model_started`, `text_delta`, `assistant`, `tool_started`, `tool_result`, `approval_requested`, `approved`, `automatically_authorized`, `denied`, `paused`, `resumed`, `cancelled`, `completed`, `failed`, `interrupted`, `context_compaction_started`, `context_compacted`. tool_result includes sanitized `result` evidence. Actual provider text_delta carries `text` and `step`, coalesced and bounded; never fabricated typing or reasoning. UI must render tool output as untrusted text, never HTML. Opaque provider reasoning_content is encrypted internally for protocol continuation but stripped from every public task/message/event.

Persistence encrypts the complete task snapshot/events with the node messaging key and atomically replaces ciphertext. On restart, running tasks become interrupted. Writes with a durable tool_started marker and no result are ambiguous and are never replayed. Approval waiting survives restart, but queued approved writes are interrupted. Cancellation stops future dispatch and retains late tool evidence; an already-started write may finish. Corrupt Agent history disables only its worker, not model sharing or the rest of node startup.

Context compaction summarizes a closed historical prefix with tools disabled. All owner messages remain verbatim, all actual mutation receipts remain pinned, retained tool calls/results stay paired, and the entire original transcript is still encrypted on disk. Checkpoints never carry execution authority. Invalid/oversized summaries fail closed. Model steps (including summary calls), active operation time (excluding approval waiting), context bytes and output bytes are bounded. Exceptions are stable codes; raw network/model exceptions are never exposed.


## Atomic sharing to one friend (2026-10-10)

`ryn_share_model_with_friend({model_id, relationship_id})` proposes one exact model/recipient change. In confirm-changes mode the owner reviews a server-generated preview containing the source revision, current scope/sharing, every saved grant (including inactive/denied relationships), relationship identities, personal-space membership and the sole intended recipient. Existing allowed recipients outside that exact target are revoked; the UI explicitly lists those revocations. Default model, Agent enablement and sibling models are outside this operation.

Activation, model scope, authoritative friend grants and the operation receipt commit in one encrypted `sources.enc` replacement under the same process-shared lock used by source/grant edits. There is no grant staging write to `permissions.json`. Legacy grants remain authoritative for services without embedded grant ownership; an activated service uses its embedded grants for catalog and signed request admission, including later owner revocation. Ordinary source edits preserve private metadata and public source responses exclude it. Model removal/readdition retains revoked revisions rather than reviving stale legacy permissions.

Reconciliation requires the co-committed receipt, matching task/owner/consumer identity, operation ID and exact argument hash; current state alone is insufficient. A missing receipt stays unknown and is not replayed. Deleting the source deletes that receipt, so attribution after deletion remains unknown. Readback proves saved scope and exact grant revisions, while receiver inference is a separate probe. Publication is refreshed after commit and its loss does not justify repeating the configuration write. Compatibility with an older binary running concurrently or a downgrade is not established by these tests; desktop upgrade acceptance remains required.


Control prompt v2.7 describes the existing approval boundary explicitly: in `confirm_changes`, a write-tool proposal stages the exact server preview and waits without dispatching the business mutation. `ryn_request_input` answers supply facts/choices; even an answer reading “approve” cannot authorize a write. Prompt and input-tool guidance are qualified to this mode so automatic mode is not misrepresented as always staging approval. No server permission or context budget changes accompany this clarification. Two new integration tests exercise the actual atomic sharing tool and confirm zero mutations before exact approval, including after a misleading approval-like input answer.

Atomic-sharing readback now also binds the committed per-model destination/rule identity and requires the current source to remain enabled and ready. Changes to that model's endpoint, credential generation, policy or availability invalidate current verification even when grants still match. Unrelated source labels and sibling model settings do not invalidate the target. Legacy receipts without a valid model binding remain attributable as executed when the durable receipt matches, but current verification is unknown; readback neither upgrades their receipt nor dispatches inference.

Control prompt v2.8 adds `operation_permissions` to main control context and checker input for current goal/scope/epoch write receipts. This is historical server evidence, never a capability for another operation or proof of success. The dispatch transaction records the consumed approval ID, operation ID, arguments/preview hashes, goal/scope/context and control revisions before invoking the tool. A whitelisted projection verifies these bindings and the corresponding server approval event; it does not read similarly named fields in tool results. Automatic-policy decisions remain distinct from explicit owner approval; legacy or inconsistent evidence is unknown, not proof that approval never happened. Read receipts remain in the full audit but are omitted from this extra projection to avoid unnecessary context growth. Checkpoint text and user-chat wording cannot supply this proof. Existing credential/header sanitization is unchanged.

## Preparation observations after an atomic share (2026-10-10)

For the registered `ryn_share_model_with_friend` operation, the same encrypted business commit may retain a bounded, private before/after projection of the target model's sharing, scope, rule revision, model settings and exact grant rows. This snapshot is not added to the public result and contains no credential. It is omitted above 24 KiB; omission keeps strict comparison rather than inventing a transition. Retiring a task removes this private snapshot with its result.

Final verification preserves the original read receipt and required criterion. A strictly later, confirmed operation in the same goal/scope/context can be a dependency of `ryn_list_models` or `ryn_inspect_services`; its registered write check runs first. The reader independently rereads current facts, then revalidates the operation's durable attribution and current target state. Only exact fields whose original values equal the committed-before snapshot may be transformed to the committed-after values. Every remaining field, model and unrelated grant must still match the fresh observation. Evidence identifies both the original observation hash and the verified write receipt/evidence used. A prior successful check alone is insufficient if the target has since changed.

This is initially registered only for atomic friend sharing and those two readers. Other writers/readers, missing legacy snapshots, invalid binding, unverified writes and multiple overlapping writes to the same target remain strict and may require fresh observations. It does not remove criteria, treat arbitrary changes as success, or replace independent semantic review of the answer.
