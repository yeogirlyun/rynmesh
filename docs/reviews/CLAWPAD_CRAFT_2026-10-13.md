## Findings and migration decisions

1. **Preserve a fixed reviewed release.** Clawpad resolves `releases/latest` on launch and accepts its accompanying checksums. Rynmesh instead uses the recorded version and SHA-256 with no automatic update resolution. A checksum binds bytes to the reviewed specification; it is not an independent publisher signature or a code audit. Future version changes require a reviewed source change.
2. **Bound downloads and extraction.** The source host rejects traversal and symlinks, but has no archive/download size or entry-count limit, and does not reject duplicate/case-colliding members. Rynmesh adds compressed/expanded/entry bounds, validates all members before writing, publishes atomically, checks installed file hashes at host startup, and retains notices. Legitimate `.htaccess` files are retained as inert distribution files and are not served by the static endpoint.
3. **Keep lifecycle local and explicit.** The source auto-installs at startup and can call native `open -a`; neither behavior is migrated. Rynmesh's installer is an explicit synchronous node-operator CLI, not a remotely callable agent operation. No native install/launch, startup download, updater, scheduler or monitor is added.
4. **Avoid the source host's busy-lock branch.** In `CraftInstaller.start_install`, the existing-worker branch returns `status()` while holding its non-reentrant lock; `status()` calls `_state()` and reacquires it. That branch can deadlock when install/update is called during installation. Rynmesh uses a separate synchronous process-shared installation lock and does not copy this worker lifecycle. No fix was applied to the owner's Clawpad checkout.
5. **Separate executable editor assets from node control.** Putting arbitrary upstream HTML/JS on the authenticated Rynmesh control origin would expose that origin's authority. Each editor instead uses a dedicated static-only port/origin with CSP, host checking and no node identity/control/upload API. Each app needs its own browser origin to isolate browser storage. The host is read-only, and serving code does not confer a grant to private workspace records.
6. **Distinguish real upstream hooks from a finished Ryn tool.** Most builds publish `window.wasmBindings`; this alone does not establish stable editing commands. EffectCraft's pinned index exposes `window.effectcraft` with `request/execute/commands/inspect`, file and browser-storage helpers. LightCraft exposes `globalThis.lightcraft.command` and documents `library.info` in its index. These are useful integration leads for Ziling; no generic remote execution bridge was invented. Each command still needs a typed contract, scoped resource authority, approval and result verification before becoming a Ryn tool.
7. **State storage and execution honestly.** Editor WASM runs in the consuming browser; a hosting node distributes static program files. Documents are in browser storage or explicitly exported files, not the encrypted JSON workspace or Exchange delivery. Browser samples are upstream fixtures. There is no shared live collaboration, job matching, automatic coin payment, registry reward or evidence of format parity from startup checks alone.

The Rynmesh migration includes all 13 catalog entries, reviewed `editor_info` calls through the existing friend/grant/receipt infrastructure, honest frontend runtime distinctions, and a standalone pinned installer/static host for the 12 web builds. Ziling's remaining work is the user launch/access path, chosen-node deployment, per-app document round-trip acceptance and any explicitly scoped editing tools.
