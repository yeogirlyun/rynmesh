## 一页看懂

**现象。** 让 Agent 按企业微信流程单号 202611030016、202611090012 做付款表，它回答“企业微信插件没有审批查询接口”，还让用户发截图。实际上 Dashboard 插件 11-04 起就提供审批查询。

**原因在 Ryn，不在中心，也不在账号权限。**
1. Ryn 只在扫码登录、手动测试等少数时候问一次中心“有哪些工具”，然后把这份清单一直存着用。中心后来新加的工具，已经登录的电脑永远看不到。
2. 插件连不上或需要重新登录时，Ryn 不告诉 Agent，直接把这个插件的工具全部拿掉。Agent 不知道是没登录，只能当成不支持。
3. Agent 不知道每个插件大概能做什么：插件列表里只有名字，没有简介；技能说明只在用户手动选中时才给。

**改法。**
1. **清单保持最新：** 本地缓存照用；每次提问前，清单超过 5 分钟没核对就问一下中心，有变化才更新。程序启动时也在后台核对一次。
2. **不可用要说清楚：** 插件需要登录、连不上、被关闭时，告诉 Agent 是哪个插件、怎么恢复。Agent 要回答“请重新登录 Dashboard”，不能说“不支持”。
3. **让 Agent 知道插件能做什么：** 每轮都附一份简短的插件能力索引（插件名、简介、技能简介）；公司插件的 Dashboard 简介补上“企业微信审批单查询”。
4. **用测试固定下来：** 以后谁改坏了，测试直接失败。

**不变的东西：** 插件不用重新打包、不用重装；中心服务不用改；没变化时不多发请求、不拖慢对话。

## 0. 执行规则

1. **只做本文列出的改动。** 没写到的文件、函数、行为都不改；不顺手优化，不重命名，不格式化无关代码。
2. **分支：** Ryn 从最新 `develop` 切出 `claude/plugin-tool-catalog`；公司插件仓库从它的 `develop` 切出同名分支。开始前看 `git status`，别人未提交的改动保持原样，不 stash、不覆盖、不删除。`docs/AGENT_STABILITY_FIX_PLAN_ZH.md` 目前未提交，不要动它。
3. **每一步单独提交**（提交信息写在各步末尾）。提交前跑完该步列出的测试，并全部通过。
4. **对不上就停。** 本文描述和代码对不上，或者改动会牵连本文没提到的文件时，停下来，写进验收文档的“待确认”一节，不要猜着改。
5. **安全底线不变：** 每次调用插件工具前，现有的绑定核对（服务器身份、版本、参数格式）照旧执行；刷新不能绕过它。

## 1. 目标

改完后，下面六条必须始终成立（第 S6 步用测试固定下来）：

| 编号 | 规则 |
|---|---|
| T1 | 中心新增或删除一个工具后，已登录的电脑最迟在 5 分钟后的下一次提问时就能看到变化，不用重新扫码，也不用点“测试”。 |
| T2 | 插件不可用（需要登录、连不上、已关闭、当前模型不允许使用）时，Agent 知道是哪个插件、什么原因，回答里会说怎么恢复，绝不说“不支持”。 |
| T3 | 每一轮 Agent 都能看到所有已启用插件的名字、简介和技能简介，不依赖用户手动选技能。 |
| T4 | 不拖慢对话：清单 5 分钟内核对过就不发请求；需要核对时各插件同时进行，最多等 3 秒，超时就先用旧清单，核对在后台继续。 |
| T5 | 核对后工具没有变化时，不改任何版本号，不打断正在运行或等待确认的工具调用。 |
| T6 | 核对失败（网络抖动、中心暂时不可用）不会丢掉旧清单，插件照常可用；只有中心明确回答“需要登录”时才改状态。 |

## 4. 设计

### 4.1 什么时候核对

| 时机 | 做法 | 等不等 |
|---|---|---|
| 程序启动后 | 对所有已启用、已登录（或不需要登录）的插件服务器核对一次 | 不等，后台进行 |
| 用户发消息后、这一回合第一次请求模型之前 | 只核对“超过 5 分钟没核对过、或状态是 NeedsTest、或清单为空”的服务器 | 最多等 3 秒；超时先用旧清单，核对在后台继续，下一次请求模型时用新的 |
| 收到 `notifications/tools/list_changed` | 安排一次核对（不受 5 分钟限制） | 不等 |
| 用户在插件页点“测试/重启” | 保持现在的做法 | 照旧 |

说明：
- 同一回合里 Agent 会多次请求模型，只有第一次请求前检查，后面几次不检查，避免回合中途清单变化。
- 需要登录的服务器不发请求，只把状态告诉 Agent（见 4.4）。
- 中心是普通 HTTP 服务，一般收不到“工具已变化”通知，所以中心主要靠“5 分钟”这一条；通知主要对本地插件有用。

### 4.2 核对怎么做

1. 在 `McpSessionManager` 里新增一个“核对清单”的方法：优先用连接池里现成的连接，没有就新建（建法同 `test_server`），只调用 `tools/list`。
2. 同一个服务器同一时间只跑一个核对，后来的直接等这一个的结果。
3. 把新清单和旧清单比较：工具名、说明、参数格式（`schema_sha256`）、只读等标注。
   - **完全一样：** 不写存储文件，不改任何版本号，只在内存里记下“上次核对时间”。程序重启后内存清空，正好由启动时的核对补上。
   - **有变化：** 走现有的 `record_mcp_discovery` 写入（版本号会变）。主人手动标的只读保留；服务器声明的只读按现有规则处理（参数格式没变才保留）。
   - **失败：** 不写清单。只有中心明确回答“需要登录”（`agent_mcp_auth_required`）才把状态改成 NeedsAuth；网络错误、超时只在内存里记“上次核对失败”，状态保持 ready，旧清单照用（T6）。
4. 写入时带上开始核对时读到的服务器身份和版本（现有机制）。如果这期间用户改了插件设置，就丢掉这次结果，不覆盖用户的改动。

### 4.3 清单真的变了时，正在进行的调用怎么办

- 工具没变（绝大多数情况）：什么都不影响（T5）。
- 工具变了：这个服务器的旧绑定按现有规则失效。正在等待确认的那次调用会被拒绝，返回 `agent_tool_definition_changed`。要确认这个错误码在界面上显示为“插件工具刚刚更新，请重新发起”，并且 Agent 能看到这个结果、重新调用。做不到就停，写进“待确认”。

### 4.4 插件不可用时告诉 Agent

1. **每轮一行状态。** 只列不可用的插件，放在开发者说明的最后（前面固定的部分不变，不影响提示缓存）。所有插件都正常时，这一行不出现。示例：
   > 插件状态：Dashboard 需要重新登录（在插件页重新扫码）；联盟 连不上服务（稍后重试或检查网络）。这些插件的工具暂时不可用，但功能是存在的。

   状态种类和恢复方法直接沿用 `plugin_catalog` 现有的 `state` 和 `recovery` 字段：需要登录 → 重新扫码；连不上 → 启动服务/稍后重试；已关闭 → 在插件页打开；当前模型不允许使用 → 换一个允许的模型（新增，对应 2.2.4）。
2. **工具搜索结果。** `ryn_discover_tools` 搜索时，如果有不可用的插件，在结果里附上它们的名字、状态和简介，让 Agent 知道“可能的工具在这个插件里，只是暂时用不了”。
3. **提示词规则。** 在 `prompt.py` 的 `SYSTEM` 里加一条（英文，和现有提示词一致），意思是：插件不可用不等于不支持，要告诉主人是哪个插件、怎么恢复，不能说这个功能不存在。按 `prompt.py` 现有做法：旧文本保存为一个新的 `_PRE_…_SYSTEM` 并加入兼容列表，`PROMPT_VERSION` 升到 `ryn-agent-loop-v14`。

### 4.5 插件能力索引

1. 每轮在开发者说明里放一份“已启用插件”索引，每个插件一行：名字 — 简介 — 它带的技能名和技能简介。
2. 长度上限：每个插件最多 200 字，总共最多 3 KB。超出时用户选中的插件优先，其余截断并注明“还有 N 个插件，用 ryn_list_plugins 查看”。
3. 内容只在插件或技能变化时才变，平时每轮一模一样，不影响提示缓存。
4. `ryn_list_plugins` 的返回加上插件简介，以及每个技能的名字和简介。
5. 技能正文仍按现在的规则：用户选中才加载。索引只是让 Agent 知道去哪个插件找工具。

### 4.6 公司插件仓库的改动

1. **简介补全。** Dashboard 的插件简介、服务器简介、技能简介都补上“企业微信付款审批单查询（按单号或按期间）”，以及中心已经提供的资金查询、数据查询这两类能力。按文件里现有的 `previous_defaults` 机制，把旧简介加进 `previous_defaults`，这样已安装的电脑导入新插件后会自动换成新简介；用户自己改过的简介不动。
2. **只读名单补全。** 把中心已经提供、而且标了只读的查询工具加进 Dashboard 的 `read_only_tools`：至少包括 `wework_approval_search`、`wework_approval_get`、`wework_approval_attachments`、`data_explore`、`journal_change_detail`，以及资金查询和借款预览工具。完整名单在实现时从中心的 `tools/list` 导出，逐个确认是只查询、不修改，才能加进去。这一项只对**新安装**的电脑生效（见 2.3.3）。
3. **已安装的电脑怎么拿到只读名单**，二选一（见第 7 节第 3 条）：
   - **做法甲（推荐，和稳定性方案一致）：** 用稳定性方案 S2b 的确认卡片。中心已经给这些工具标了只读，Ryn 会把它们列为“建议只读”，Agent 页弹一次卡片，主人点“允许”后生效。Ryn 不需要为此另外改代码。
   - **做法乙：** 改 `migrate_release_defaults`，允许已签名的公司插件在升级时**新增**只读工具。条件是：只加不减；中心那边也标了只读；主人改过的不动。这会放宽 10-21 的安全设计，需要你明确同意。
4. 单独分支、单独构建、单独记录版本。打包并在 Ryn 里导入新插件后才生效。

### 4.7 新旧版本搭配

| 组合 | 结果 |
|---|---|
| 新 Ryn + 旧公司插件 | 清单会刷新，审批查询能用；但审批查询被当成写操作，确认模式下每次都要弹窗确认。 |
| 旧 Ryn + 新公司插件 | 简介更新了；清单仍然不刷新，老问题还在。 |
| 新 Ryn + 新公司插件 | 全部生效。已安装电脑的只读名单按 4.6 第 3 条处理。 |

存储格式不变：“上次核对时间”只放内存，不加持久字段，不需要数据迁移。

## 5. 修改步骤

### 阶段 0：主机核对（不改代码）

在出问题的那台电脑上，打开“插件 → Dashboard”，记下：状态、工具数量、上次连接时间、工具列表里有没有 `wework_approval_get`。然后点“测试”，再问一次同样的问题，记下结果。这样能确认是“清单太旧”还是“登录失效”，结果写进验收文档。

### 阶段 1：Ryn

**S1 文档入库**
- 把本文件加入仓库。
- 提交信息：`docs: plan plugin tool catalog freshness`

**S2 核对清单的方法**
- 改 `extensions/mcp_transport.py`：按 4.2 新增核对方法、同服务器只跑一个、内存里的核对时间和失败记录。
- 改 `extensions/store.py`：只在“有变化”时调用现有的 `record_mcp_discovery`；如需比较函数，放在 store 里，和现有的参数格式哈希用同一套算法。
- 测试：工具没变时版本号不变、存储文件不写；工具变了才写；网络失败保留旧清单且状态不变；需要登录时状态变 NeedsAuth；核对期间用户改了设置，结果被丢弃。

**S3 核对时机**
- 程序启动：Agent 运行时创建好之后，起一个后台线程做一次核对（写法参照 `runtime._schedule_idle_storage_relief`）。
- 每回合开始：在 `loop._model_turn` 里调用 `self._menu(selected)` 之前，判断这是不是本回合第一次请求模型；是的话，按 4.1 的规则核对，最多等 3 秒。
- 通知：`StdioMcpSession` 和 `StreamableHttpMcpSession` 收到 `notifications/tools/list_changed` 时，通知 `McpSessionManager` 安排核对；这类通知不计入 64 条的上限。
- 测试：5 分钟内不重复核对；超过 5 分钟才核对；核对超过 3 秒时先用旧清单、下一次请求用新清单；同一回合中间的请求不核对；收到通知会核对。
